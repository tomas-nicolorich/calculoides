# Bug Report: Savings Goal Projected Date is Epoch (1/1/1970)

**Type**: Implementation drift
**Severity**: High
**Feature**: 001-calculoides-core-app

## Description
The "projected completion date" displayed in the Savings Goal section of the UI is consistently showing "1/1/1970" (Unix Epoch). This occurs regardless of the target amount, contribution overrides, or current progress, rendering the projection feature unusable and misleading for users.

## Artifact Traceability

### spec.md
- **Affected user story**: User Story 3 — Savings Goals & Proportional Contributions
- **Affected requirements**: 
  - **FR-006**: "If contributions are overridden, the system MUST recalculate the projected date and display the variance from the original target date."
  - **SC-011**: "Savings goal projections and contribution values MUST be updated in the UI within 500ms... without requiring a page reload."
- **Gap identified**: None in the spec; the requirement for dynamic projections is clear. This is an implementation failure.

### plan.md
- **Affected sections**: Summary (Backend/Logic section for savings projections), Technical Context (Savings goal contribution overrides).
- **Impact**: The calculation logic in the backend and the date representation in the frontend need to be synchronized and fixed to handle valid date ranges.

## Root Cause Analysis
The date `1/1/1970` suggests that a numeric value of `0`, `null`, or an invalid calculation result (like `NaN` or `Infinity` from a division by zero) is being passed to a `new Date()` constructor or a date formatting utility. 

Potential areas of failure:
1. **Backend**: `SavingsService.calculateProjectedDate` might be returning `0` or `null` if the contribution amount is not correctly retrieved or if the logic for adding months to the current date is flawed.
2. **Frontend**: The API response might contain a timestamp of `0`, or the frontend code might be failing to parse the backend's date format, defaulting to `0`.
