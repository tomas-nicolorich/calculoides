# Bug Report: Savings goal contribution update not reflected in UI without reload

**Status**: Patched
**Patched**: 2026-06-02
**Type**: Implementation drift
**Severity**: Medium
**Feature**: 001-calculoides-core-app
**Reported**: 2026-06-02

## Description
When a user updates a savings goal contribution amount, the changes are successfully saved to the backend (verified by page reload), but the UI does not update instantly. The user is forced to refresh the page to see the updated contribution shares and the recalculated projected completion date.

## Artifact Traceability

### spec.md
- **Affected user story**: User Story 3 — Savings Goals & Proportional Contributions
- **Affected requirements**: 
    - **FR-006**: "If contributions are overridden, the system MUST recalculate the projected date and display the variance from the original target date."
    - **SC-011**: "Savings goal projections and contribution values MUST be updated in the UI within 500ms of a successful contribution override without requiring a page reload (BUG-031)."
- **Gap identified**: None. The specification explicitly mandates this behavior. This is a clear case of implementation drift or regression.

### plan.md
- **Affected sections**: Phase 5 (US3: Savings Goals)
- **Impact**: The frontend mutation logic for updating contributions needs to be updated to either invalidate the relevant cache (e.g., TanStack Query) or perform an optimistic update to ensure the UI reflects the new state immediately.

### tasks.md
- **Affected tasks**: 
    - **T110**: Implement UI state synchronization for savings goals in the contribution update mutation.
    - **T111**: Add an automated UI test to verify that savings goal projections update immediately after a contribution change without a reload.
- **False completions**: **T110** is marked as complete but the reported behavior indicates it has regressed or was not fully implemented for all edge cases.
- **Missing tasks**: None. Completion of **T111** is critical to prevent future regressions.

## Root Cause Analysis
The issue is likely due to the frontend mutation (`useMutation`) not correctly triggering a refetch or cache invalidation for the savings goal data after a successful contribution update. While **T110** was intended to fix this, the lack of an automated test (**T111**) allowed a regression to occur or allowed an incomplete fix to be merged.
