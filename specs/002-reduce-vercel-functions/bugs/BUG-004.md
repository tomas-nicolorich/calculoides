# Bug Report: TypeError in InvitationList on Dashboard

**Type**: Implementation drift
**Severity**: Critical
**Feature**: 002-reduce-vercel-functions
**Reported**: 2026-05-21
**Status**: Patched
**Patched**: 2026-05-21

## Description
Logged-in users see a blank page instead of the dashboard content, and the browser console reports an `Uncaught TypeError: Cannot read properties of undefined (reading 'name')` at `InvitationList.tsx:59:74`. This occurs during the initial load of the dashboard when the application attempts to fetch pending invitations.

## Artifact Traceability

### spec.md
- **Affected requirements**: FR-004 (All public-facing API endpoints MUST maintain their original behavior and response format).
- **Gap identified**: The specification failed to account for logical endpoints that handle multiple HTTP methods (e.g., `/api/invitations` handles both `GET` for listing and `POST` for creating). The consolidation strategy assumed a simple 1:1 mapping between logical routes and action-based dispatcher handlers without considering method-based dispatching.

### plan.md
- **Affected sections**: Phase 3 (Consolidation Strategy), Phase 5 (Compliance - Rewrites).
- **Impact**: The mapping of the `/api/invitations` endpoint is incomplete. The current plan does not ensure functional parity for the `GET` behavior of this endpoint.

### tasks.md
- **Affected tasks**: 
  - `T011`: [US1] Implement consolidated Groups handler (incomplete invitation logic).
  - `T017`: [US2] Remove `api/invitations.ts` (removed before full parity was established).
  - `T021`: [US3] Update `vercel.json` rewrites (incorrect mapping for listing).
- **False completions**: 
  - `T011` is marked [X] but the `invitations-list` action is unreachable via the standard logical endpoint.
  - `T021` is marked [X] but the rewrite for `/api/invitations` only supports the `invite` (POST) action.
- **Missing tasks**:

## Root Cause Analysis
During the consolidation of `api/invitations.ts` into `api/src/handlers/groups.ts` (T011, T017), the original logic was split into two actions: `invitations-list` (for listing) and `invite` (for creating). However, the `vercel.json` rewrite for `/api/invitations` only maps to `action=invite`. Because `vercel.json` rewrites are method-agnostic, `GET` requests to `/api/invitations` are sent to the `invite` action, which returns a 400 error due to missing body parameters.

More importantly, if the dispatcher or server fails to correctly resolve the action, it defaults to `list`, which returns an array of **Groups** instead of **Invitations**. The frontend `InvitationList` component receives this array of Groups and attempts to access `invitation.group.name`. Since Group objects do not have a `group` property, this results in a `TypeError`.

## Recommended Fix
1. Run `/speckit.bugfix.patch` to update `spec.md` with requirement for method-aware routing for multi-purpose endpoints.
2. Modify `api/src/handlers/groups.ts` to merge `invitations-list` and `invite` into a single `invitations` action that branches based on `req.method`.
3. Update `vercel.json` to map `/api/invitations` to `action=invitations`.
4. Run `/speckit.bugfix.verify` to confirm that `GET /api/invitations` returns the correct data format.
5. Resume `/speckit.implement` to apply and verify the fix.
