# Bug Report: BUG-014 - Inconsistent User Display (Name only)

**Type**: Spec gap | Implementation drift
**Severity**: Medium
**Feature**: 001-calculoides-core-app
**Reported**: 2026-05-15
**Status**: Patched
**Patched**: 2026-05-15

## Description
Users are currently displayed inconsistently across different views. In most views, they are shown by their email address, while in the members section, they are shown by their unique ID. The intended behavior is that everywhere a user is displayed, it should show their name only.

## Artifact Traceability

### spec.md
- **Affected user story**: 
    - US1 - Group Setup & Income Distribution
    - US2 - Budgeting & Spending
    - US4 - Budget Transfers & Archiving
- **Affected requirements**:
    - FR-004: Dashboard display requirements.
    - FR-008: Member management and visibility.
- **Gap identified**: The specification lacks a explicit UI requirement for user identification, resulting in developers using technical identifiers (ID/Email) instead of the `name` field.

### plan.md
- **Affected sections**: Technical Context -> Frontend (React/FSD).
- **Impact**: The frontend implementation must be audited to ensure that the `User.name` property is always prioritized for display.

### tasks.md
- **Affected tasks**: 
    - `T019`: [US1] Implement Group Member list and Invitation UI (currently using IDs).
    - `T026`: [US2] Implement Dashboard Summary widget (currently using Emails).
    - `T027`: [US2] Create Category list and Expense entry UI (currently using Emails).
    - `T032`: [US3] Implement Savings Goal widget.
    - `T039`: [US4] Implement Transfer UI.
- **False completions**: 
    - T019, T026, T027, T032, T039 are marked as complete but do not meet the newly clarified requirement for name-only display.
- **Missing tasks**:
    - Create a shared `MemberName` or `UserDisplay` component in `frontend/src/shared/ui/` to standardize display logic.
    - Update API responses to ensure `name` is always included in member/user relations.

## Root Cause Analysis
Spec oversight. While the data model included a `name` field, the functional requirements and success criteria did not specify that this field must be the exclusive way to represent users in the UI. This led to implementation drift where developers used the most convenient unique field available in the current context.

## Recommended Fix
1. Run `/speckit.bugfix.patch` to update `spec.md` with a new requirement (e.g., FR-015) for consistent user display.
2. Run `/speckit.bugfix.verify` to confirm artifact consistency.
3. Resume `/speckit.implement` to refactor the frontend components and ensure API hydration includes user names.
